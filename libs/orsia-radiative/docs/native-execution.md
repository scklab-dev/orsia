# Native propagation and execution

This developer reference describes the packaged serial kernels, precision dispatch and buffer ownership. Public physical controls are specified in the [transfer reference](transfer.md).

## Compiled propagation

The `transfer/native/` package groups the compiled extension, its type stub and its C++ sources: `transfer_native.cpp`, `transfer_native.pyi`, `orders_native.h`, `solar_tangent_native.h`, `scattering_tangent_native.h`, `thermal_native.h` and their numerical kernel headers. Direct-solar and thermal tangent bindings are separate from pointer-based physical kernels. The scattering tangent binding uses derivative companions for native formal preparation, phase evaluation and recurrence. Python entry points remain in `transfer/formal.py`, `transfer/orders.py` and `transfer/thermal.py`, with the existing root and transfer APIs.

Package builds require a C++17 compiler and CPython headers; setuptools and the pinned pybind11 build dependency build `transfer.native.transfer_native` for the target interpreter, including CPython 3.14 free-threaded. Compilation errors are surfaced by the build. Wheels are platform/interpreter-specific. The extension uses the Python buffer protocol and pybind11's NumPy array allocation boundary. The build uses CPython, pybind11 and installed Numerics headers, and packaged execution uses the declared NumPy/SciPy runtime dependencies. Numerical kernels take typed pointers and sizes independently of the binding; formal preparation uses the same thin-cell and opaque-limit formulas in native and NumPy paths. Propagation preserves the recurrence operation order; Rayleigh products and reflection use the arithmetic described below.

The internal native `prepare` and `apply` entry points remain positional-only and return `None`, writing directly into caller-provided buffers. They accept general C-contiguous buffer exporters with matching native `f` or `d` formats, including `array.array` vectors and multidimensional `memoryview` matrices, without conversion or copying. Inputs may be read-only; outputs must be writable and disjoint. Acquisition preserves exporter-specific contiguity/writeability exceptions; dtype and grid validation raise `ValueError`. Buffer exports remain live throughout the detached numerical call and are released with the Python thread state attached on both success and failure. Exit-only application does not acquire the unused centre coefficients. The extension declares free-threading and per-interpreter support; the isolated native module is tested in a subinterpreter with standard-library buffers, not the NumPy/SciPy package import surface.

`transfer.formal.apply_propagation` selects the serial native recurrence for matching native float32 or float64 arrays, copying noncontiguous inputs when necessary; its signature and physical model are unchanged. The NumPy recurrence handles mixed precision and arrays outside the native float/double ABI. No fast math or fused multiply-add is enabled. Sources and coefficients must not be mutated during a call; outputs are fresh, and concurrent calls may share immutable inputs. The internal buffer entry points are not supported consumer APIs and require fresh output buffers disjoint from each other and from inputs.

`transfer.formal.propagation_coefficients` also uses fused serial native preparation for matching float32/float64 vector inputs on small grids (at most 32 directions) or strongly repeated grids (at most 1024 directions, at least half exact repeated signed cosines). Reuse is call-local and exact, not an angular approximation or persistent cache. Finite nonpositive endpoint integration uses `exp(max(a,b))*exprel(-abs(b-a))`. Thick constant-source weights divide by vertical depth directly, avoiding overflow in the slant-depth quotient. Nonfinite beam exponents use the corresponding vertical-depth opaque limit; the scattering tangent differentiates that limit. Coefficients remain owned read-only snapshots. Large unique-angle grids use full-grid NumPy/SciPy vector operations because scalar native transcendental functions can be slower. Inputs must remain stable during preparation. The six solar coefficient matrices are unchanged; native preparation uses call-local scratch without matrix-sized temporaries, while the NumPy fallback builds full-grid temporary arrays.

Float32 depth and direction arrays select float32 coefficient buffers and native `expf`/`expm1f` arithmetic (or dtype-preserving NumPy/SciPy fallback); a float64 geometry input promotes preparation to float64. Application returns float32 centres and exits only when both source and coefficients are float32; mixed precision promotes both outputs to float64, without downcasting the higher-precision input. Solar cosine and bottom radiance scalars are rounded to the selected array precision; solar cosine must remain positive and at most one after rounding. Float64 callers retain their existing precision and defaults. Coefficient buffers remain owned read-only snapshots, and exit-only application and repeated reuse support both precisions. Float32 halves coefficient storage but has less exponent range and more accumulated roundoff; suitable precision depends on optical depth, direction cosines, cell count and cancellation in signed sources. This path covers the formal operator, not an end-to-end float32 solar or thermal solver, and introduces no changes to angular grids, subdivisions or scattering settings.

Run `devbox run -- just rebuild-native` after editing native source, then `devbox run -- just typecheck` and `devbox run -- just --justfile tests/justfile pytest libs/orsia-radiative/tests tests/test_core_imports.py` for equivalence, dtype, edge, concurrent-call and imported-runtime checks. The one-off propagation-dtype benchmark is retired; existing local measurements are historical formal-operator observations, not complete solar-call timings. These are software checks, not instrument-space or retrieval qualification; prototype timing evidence does not establish packaged speed on every platform.

## Direct cross-section optical depth

`optics.cross_sections.cross_section_optical_depth` calls the dedicated `absorption_native.cross_section_optical_depth` entry. The binding checks native float64 buffers and nonempty matching support, adapts storage, and allocates one depth output. Its pointer-only direct loop shares column validation and checked multiplication with the fused tangent loop. The tangent computes values and directions together. Each call detaches once and owns writable output storage.

Table and measured cross-section evaluation use this direct primitive. The spectroscopy adapters promote stored numerical arrays to float64 before the native boundary, retain physical checks, and return `AbsorptionComponent`. The fused `spectroscopy/lines.py` path is unchanged. See the [array contract](spectroscopy.md#cross-section-optical-depth-arrays) for units, shapes and invalid-input behavior.

## Shared explicit directional tangents

The existing setuptools/pybind11 build also compiles `optics.absorption_native` for fixed-cross-section optical depth and its directional tangents. This separate optical kernel keeps optical composition independent of transfer imports. `transfer.native.transfer_native` binds direct reflected-solar values and tangents from `solar_tangent_native.h`. Both extensions declare free-threading support. The absorption and direct-solar entries detach once per serial calculation. The thermal binding extends the existing kernel with component and total tangents for both hemispheric methods. Absorption, solar and thermal kernels use shared scale and product-rule operations from `<orsia_numerics/tangent.h>`; Radiative owns all physical laws and partial derivatives.

The optical kernel multiplies each fixed cross section by the molecular column and each signed column direction. The solar kernel reuses the direct-value attenuation helper and balanced layer reduction from the value calculation. It propagates optical-depth and reflectance directions analytically with runtime last-axis `k`, including zero. Input arrays remain live during computation; noncontiguous or unaligned storage receives an aligned contiguous copy without modifying inputs. Outputs are separately owned NumPy arrays. Native float64 is required without implicit precision conversion; there is no finite-difference fallback.

The fixed-order solar tangent entry in `scattering_tangent_native.h` reuses primal coefficient preparation, phase evaluation, dense redistribution and balanced flux reduction. Analytical companions supply HG and retained Delta-M coefficient derivatives, stable thin-cell and equal-exponent integral limits, and coupled value/tangent formal sweeps. The binding first uses the existing spectral-order calculation for primal validation and returned values. It then processes directions serially with one direction's scratch. The supported Python entry binds the existing SciPy LP64 BLAS pointer for primal and tangent redistribution. A call-local FIFO cache stores HG phase matrices and their unseeded `g` partials across layers, orders, points and directions. Its payload budget is 16 MiB; a larger phase/partial pair uses one temporary pair. Seed-dependent matrices combine these cached values with current depth and asymmetry seeds, so equal primal `g` values can have different seeds. The private unbound native entry retains scalar redistribution for regression tests. Empty direction blocks return validated primal values without derivative scratch. Zero primal source and boundary amplitudes retain their derivatives. Actual-amplitude boundary sweeps preserve the existing underflow fallback.

Scattering inputs use retained native float64 buffer exports with stride-aware, alignment-safe reads. Arrays remain stable throughout the call, and buffer releases run with the Python thread state attached. Outputs and scratch belong to the call. The package's free-threading declaration also covers this entry; bounded concurrent-call tests establish only their tested cases.

See the [public tangent contracts](transfer.md#solar-sos-constituent-tangents) for physical coverage, units, shapes and failure behavior. Run `devbox run -- just --justfile tests/justfile pytest libs/orsia-radiative/tests/test_absorption_solar_tangents.py libs/orsia-radiative/tests/test_scattering_tangents.py` after rebuilding for analytical, finite-difference-reference, refinement, ownership, concurrency and fresh-import GIL checks. The tests use at most two Python workers; execution policy remains caller-owned.

### Header packaging and isolated builds

Radiative declares `orsia-numerics==0.1.0` as an explicit build dependency. `setup.py` resolves `orsia_numerics.get_include()` from the build environment. Numerics source distributions and wheels carry the header. A source build needs a wheel or source distribution for Numerics available to its resolver; it does not need a neighbouring checkout. When staging packages, build Numerics first and supply its wheel directory through `--find-links`. Rebuild Radiative after changing the shared header.

`devbox run -- just python scripts/validate_tangent_distribution.py` builds archived sources with `--no-sources`, then installs the resulting wheels into an independent environment. The check verifies header inclusion, Numerics Jacobians, native direct/tangent absorption, public SOS/Delta-M constituent tangents, thermal spectral/band evaluation, general linear operators and dense MAP fitting and disabled GIL after native imports. Compiler include paths resolve the header from installed build-environment site-packages. The check leaves source distributions and wheels in `outputs/tangent-distribution/` and removes its temporary environment.

### Bounded thermal timing

The installed-package example `scripts/thermal_tangents.py` evaluated a synthetic 16-layer, 512-point scene on macOS arm64 with CPython 3.14.3 free-threaded. Each reported median used seven serial full-model calls after one warmup, including Python state composition and native transfer. Numerical thread limits were one and concurrent builds were limited to two. Both methods preserved a disabled GIL after imports.

| Method | Value only [ms] | 1 direction [ms] | 3 directions [ms] | 4 directions [ms] |
| --- | ---: | ---: | ---: | ---: |
| Exponential integrals | 0.707 | 1.878 | 1.992 | 2.050 |
| Quadrature, order 32 | 1.147 | 1.608 | 1.964 | 2.427 |

These observations cover this synthetic scene and local installed build. They establish neither a general speedup threshold nor broad scientific qualification. The script reports the environment, selected spectral values, band Jacobian and raw median seconds for reproduction.

## Solar boundary-response reuse

Solar SOS prepares the discrete unit-amplitude Lambertian boundary response once per active spectral point and scales it for the initial surface field and subsequent reflected orders. The response uses the existing cell recurrence and centre convention; each atmospheric order still propagates its full diffuse source. Buffers belong to the current evaluation and spectral point. Any subnormal or zero upward unit exit selects the original actual-amplitude boundary sweeps, preserving exponent range in extreme attenuation. Scaling changes rounding at floating-point precision while preserving the physical model, public API, spectral support, angular grid and order controls. The additional retained response occupies one float64 cell/direction matrix and one exit vector, independently of the number of orders and spectral points.

Run `devbox run -- just --justfile tests/justfile pytest libs/orsia-radiative/tests/test_solar_boundary.py` for repeated-sweep regression tests. The historical Git-baseline timing runner has been retired; numerical boundary-response regressions remain in the library test suite.

## Solar order accumulation

Packaged SOS evaluates the full spectral grid in one detached C++ invocation: physical extinction summation and overflow checking, optional Delta-M transformation, subcell preparation, direct reflection, transport coefficients, direct-beam scattering, diffuse redistribution and Lambertian surface coupling. Rayleigh components with at least three physical layers use the exact seven-factor expansion, including sparse and mixed scenes; smaller Rayleigh scenes and HG aerosol use dense phase operators. A call-owned FIFO phase cache retains up to 16 MiB of operators, with larger operators applied from temporary storage. Spectral points run serially and reuse the same transport and field buffers; successive orders retain the preceding angular field. Angular quadrature, public support validation, domain extraction and final `Radiance` assembly remain in Python.

The matrix products use SciPy's native `dgemm` pointer, resolved once when `orders` imports from the LP64 Cython capsule supplied by the supported environment. The interpreter-local callable retains the exporting module for the pointer's lifetime. Native balanced flux reduction and the shared formal sweeps complete each order. The detached region operates exclusively on exported buffers, scalar values and native-owned storage. Scalar source scaling and boundary operations use strict separate multiplication/addition; BLAS retains its backend arithmetic. Numerical regression uses `rtol=3e-14, atol=0` for retained boundary cases and `rtol=3e-13, atol=0` for expanded mixed/Delta-M cases; independent ray tests assess the same discrete physical model.

Keep borrowed inputs stable throughout the call, including concurrent evaluations. The native boundary supports native float64 C-layout, F-layout, signed strides and unaligned storage through retained buffer exports; other input precision is promoted at the Python boundary. Scratch and fresh writable float64 `(order, point)` output belong to one invocation. Public signatures and numerical controls retain their existing meanings. The compiled extension and fixed SciPy LP64 BLAS signature are supported-environment invariants; `orders` and `formal` import the extension directly, and `orders` binds BLAS at module load. The formal operator retains its separate float32/float64 behavior. BLAS thread policy remains caller-controlled.

Run `devbox run -- just --justfile tests/justfile pytest libs/orsia-radiative/tests` for arithmetic, ownership, stride, error, portable-native and concurrent-call regressions. The frozen Python recurrence lives in the test suite as an explicit reference.
