# Observation geometry and orbital adapters

## Time, support and ownership

`compute_lines_of_sight(times_s, epoch=..., validity_s=..., output_frame="GCRS", ...)` uses a timezone-aware UTC `datetime` with zero UTC offset. Each numerical time is physical elapsed SI seconds from that instant. Callbacks receive those seconds unchanged. Callback owners must preserve continuous-time semantics across leap seconds; naive UTC subtraction is unsuitable. The default GCRS path performs no time-scale conversion. ITRF/TEME output converts elapsed seconds through the SatKit adapter.

The finite closed `validity_s=(start,end)` interval covers every callback. Endpoints are included. Times can repeat, arrive out of order or be empty. Invalid output frame, epoch or support fails before a callback or backend runs. Callers intersect all trajectory, attitude and auxiliary validity intervals before evaluation. Core array operations perform no network access or extrapolation. SatKit adapters follow the resource policy below.

Trajectory callbacks return finite float64 `(times,3)` GCRS positions in metres and velocities in metres per second. Attitude callbacks return proper float64 `(times,3,3)` matrices. The supplied trajectory owns interpolation and accuracy. Callback inputs and outputs are borrowed unchanged during the call. Callbacks remain pure and stable during evaluation; callers own callback lifetime and concurrent-use safety. Geometry returns independent writable float64 arrays and never retains callback references after `compute_lines_of_sight` returns. Empty ray/time axes remain empty.

Array-only functions borrow finite float64 arrays. No input array is modified. Returned arrays own writable storage, except validation functions which return no value. Proper rotations satisfy orthogonality and determinant +1 with absolute tolerance `1e-10`. Unit directions use the same absolute norm tolerance. Numerical shape/physical-domain failures raise `ValueError`; callback exceptions propagate.

## Frames, attitude and mounts

Matrices act on column vectors. `R_G_P` maps platform to GCRS and `R_P_I` maps instrument to platform. +instrument-z is the surface-directed boresight. A fixed platform offset `b_P` locates the optical origin. Composition is `origin_G = r_G + R_G_P @ b_P` and `direction_G = R_G_P @ R_P_I @ direction_I`.

`compose_rays` accepts position shape `(...,3)`, matching platform rotations `(...,3,3)`, relative rotations `(3,3)` or `(...,3,3)`, shared instrument directions `(rays,3)` and one offset `(3,)`. Both returned arrays have shape `(...,rays,3)`. `compute_lines_of_sight` supplies the one-dimensional time leading axis. Relative attitude callbacks can implement moving mounts or caller-defined scans independently of trajectory and platform pointing.

`compute_lines_of_sight` returns origins in metres and unit directions in `output_frame`, each shaped `(times,rays,3)`. The default `"GCRS"` output uses NumPy only. `"ITRF"` and `"TEME"` use `frame_rotations` internally to apply the same dated rotation to both arrays. Each vector represents a ray coordinate, so this operation needs no velocity derivative or shifted auxiliary dates. Unsupported frame names raise `ValueError` before callbacks or backend use. Callback exceptions propagate unchanged; missing EOP coverage or failed backend evaluation raises `RuntimeError`. An `ImportError` indicates that the required SatKit installation cannot load. Native calls can acquire public auxiliary files and use process-global caches under the resource policy below.

`transform_rays(times_s, origins_m, directions, epoch=..., validity_s=..., from_frame="GCRS", to_frame="ITRF")` expresses existing dated rays in another Earth-centred frame. Origins and unit directions have matching `(...,3)` shapes; times match the leading axes exactly. Scalar and empty leading axes are supported. The helper privately flattens times, evaluates each distinct date once through `frame_rotations`, and restores the original axes, order and repetitions. Both outputs own writable float64 storage and inputs remain unchanged. The same dated rotation acts on each origin and direction, with no velocity derivative or auxiliary padding. Epoch, closed time support, frame choices, required SatKit installation and EOP requirements follow `frame_rotations`, including identity transformations' lazy backend import.

WGS84 intersection and visibility inputs use Earth-centred ITRF Cartesian x, y, z coordinates in metres. Request ITRF rays before applying those operations; the surface functions perform no frame conversion. The `frame_rotations` adapter maps GCRS axes to SatKit GCRF and uses full IERS 2010/IAU 2006-2000A reductions for ITRF and TEME. This convention excludes solid/ocean tides and any site-specific terrestrial realization correction. `transform_states` includes the time derivative of the complete rotation for position/velocity states. Trajectory and platform-attitude callbacks supplied to `compute_lines_of_sight` always use GCRS, regardless of the selected output frame. Transform terrestrial state vectors and attitudes explicitly when defining those callbacks.

## Analytic surfaces

`sphere_intersections(origins_m, directions, radius_m=...)` uses a positive radius in metres in the rays' common frame. `ellipsoid_intersections(origins_m, directions)` fixes the WGS84 reference ellipsoid internally at ellipsoidal height zero. The [LEO ground-trace example](../README.md#construct-a-leo-trajectory-and-ground-trace) requests ITRF output from `compute_lines_of_sight` before the separate intersection call. WGS84 intersections and visibility exclude terrain, geoid heights and atmospheric ray bending. The array-only surface core depends only on NumPy and performs no auxiliary access.

`orsia_geometry.constants` owns `WGS84_SEMIMAJOR_AXIS_M` and `WGS84_INVERSE_FLATTENING`, the defining shape scalars. `WGS84_FLATTENING` and `WGS84_SEMIMINOR_AXIS_M` derive from them. `WGS84_SEMIAXES_M` is an immutable tuple in ITRF x, y, z order; the z axis uses the polar semiminor axis. The module cites NGA's WGS 84 defining parameters and GeographicLib's independent `Constants::WGS84_a` and `Constants::WGS84_f` implementation. This surface choice leaves the distinct WGS72/AFSPC SGP4 and EGM96 force-model conventions unchanged.

The previous `semiaxes_m` keyword has been removed from `ellipsoid_intersections` and `surface_visibility`. Migrate WGS84 callers by supplying ITRF arrays and omitting the keyword. Arbitrary ellipsoids are outside these APIs; the separate sphere API retains its explicit radius.

Both intersection functions accept matching `(...,3)` origins and unit directions. Both return Boolean hit mask `(...)` and points `(...,3)` in metres. The selected root is the nearest nonnegative ray distance. Tangencies hit when the float64 discriminant is nonnegative. Surface-origin rays hit at distance zero, including outward rays. Inside-surface origins use the forward exit. Misses have false status and NaN coordinates while the input ray remains valid. The stable quadratic-root calculation avoids cancellation in the smaller root. The float64 discriminant is used without horizon snapping; near-tangent cases remain ill-conditioned.

`surface_visibility(observers_m, targets_m)` accepts exterior ITRF observers and matching WGS84 height-zero targets in metres. Surface membership requires dimensionless ellipsoid residual at most `1e-10`. Visibility is the sign of the outward-normal projection from target toward observer. Tangent viewing is included. Tracking rotations remain defined for occluded targets; visibility is a separate geometric mask.

### Fixed local east/north chart

`project_local_east_north(points_itrf_m, origin_itrf_m=...)` projects displacements onto an explicit origin's fixed WGS84 tangent plane. The origin is finite `(3,)` ITRF metres at ellipsoidal height zero, with `abs(sum((origin/axes)**2)-1) <= 1e-10`. Exact pole origins (`x=y=0`) raise `ValueError` because east is undefined. The normal is the normalized ellipsoid gradient `origin/axes**2`. East follows increasing longitude; north completes the orthonormal chart basis. The chart discards normal displacement and returns projected distances rather than geodesic distances.

Input points have shape `(...,3)` and may lie off the ellipsoid. Each triplet is finite or all NaN for a missed ray; partial NaN or infinite triplets raise `ValueError`. Owned writable float64 outputs have shape `(...,2)`, ordered east, north in metres. All-NaN triplets remain all-NaN pairs. Scalar and empty leading axes are preserved and inputs remain unchanged.

`WGS84SurfaceProjection(epoch=..., validity_s=..., chart_origin_itrf_m=...)` constructs a callable object `surface(origins_gcrs_m, directions_gcrs, times_s) -> (xy_m, view_local, hits)`. Construction validates the UTC epoch, finite closed interval and nonpolar height-zero origin, and snapshots the retained chart input without loading SatKit. Evaluation composes GCRS-to-ITRF `transform_rays`, `ellipsoid_intersections` and the local east/north projection. Ray arrays have matching `(...,3)` shapes and times exactly match `(...)`; outputs are owned writable `(...,2)` coordinates, `(...,3)` outward surface-to-sensor unit views, and Boolean `(...)` hits. Views use the fixed chart-origin east/north/up Cartesian basis after the dated GCRS-to-ITRF rotation. This basis is shared with the scene; it has no per-intercept ENU rotation. Missed rays retain finite transformed views and NaN coordinates. Nearest-forward, surface-origin, inside-origin, tangency and NaN-miss semantics follow the intersection primitive. Evaluation preserves inputs and uses the same deferred-import and EOP contracts as `transform_rays`.

`WGS84SurfaceProjection.from_ray(origin_gcrs_m=..., direction_gcrs=..., time_s=..., epoch=..., validity_s=...)` chooses the chart origin from one explicit reference ray. Supply finite `(3,)` GCRS x/y/z metres, a finite `(3,)` scene-directed unit vector with absolute norm tolerance `1e-10`, and scalar physical elapsed SI seconds. Epoch and finite closed support follow `transform_rays`. Construction uses that dated GCRS-to-ITRF transformation and `ellipsoid_intersections`, then constructs `WGS84SurfaceProjection` with the nearest forward intercept. A missed reference ray or exact-pole intercept raises `ValueError`. Construction uses SatKit and requires EOP coverage; import and backend errors propagate. The retained chart and interval are snapshots; reference arrays remain unchanged and are not retained. The returned callback has the same axes, ownership, hit/miss and time-support contract as the explicit-origin factory.

The explicit-origin, from-ray and Instruments camera constructors all return that same class. Its `epoch` and `validity_s` bindings are immutable; `chart_origin_itrf_m` returns an independent writable copy. Changing this copy leaves the cached chart basis unchanged.

Reuse one surface callback when comparing simulation and estimated geometry to keep the chart origin and axes fixed. Both factories supply sampled intersections; continuous visibility, projection support and motion/angular bounds remain caller responsibilities. Terrain and atmospheric ray bending are excluded. Instruments owns `wgs84_surface_projection_from_camera`, which composes camera intrinsics and platform geometry through `compute_lines_of_sight`, then calls the single-ray factory. The [fixed-filter camera walkthrough](../../orsia-instruments/docs/filter-camera.md#walkthrough-two-strips-over-earth) uses that higher-level helper. Geometry has no Instruments dependency.

## Roll, targets and scans

`radial_nadir` sets +platform-z toward the centre and +platform-x along the projection of inertial velocity onto the transverse plane. +y completes the right-handed triad. Ellipsoid-normal nadir is a separate convention and is outside this helper.

`platform_tracking` points +platform-z from the platform reference point toward the supplied target. This helper requires an exactly zero `(3,)` mount offset and assumes the tracked optical boresight aligns with +platform-z. Use general composition for nonzero offsets. `instrument_tracking` points +instrument-z from a supplied optical origin and returns the relative rotation under an independently supplied nominal platform attitude. The caller includes any offset in that optical origin.

Both tracking helpers project a caller-supplied GCRS roll-reference vector onto the boresight-transverse plane to define +x. The reference can represent motion or another explicit roll choice. Coincident target and origin fail. Zero or nearly parallel references fail when their transverse norm is at most `1e-12` times their total norm. Supplied target positions must include the selected target motion; an Earth-fixed ground target requires an explicit dated frame transformation.

`axis_rotations` constructs right-handed rotations from a unit axis and caller-supplied angles in radians. For example, an `instrument_attitude(times)` callback can return `axis_rotations(np.array([1.,0.,0.]), scan_angle(times))`. Multiplication order determines whether a scan is platform-relative or instrument-relative. Off-axis rays retain the full computed roll and field rotation.

`attitude_interval_speeds` returns the principal relative-rotation angle divided by each interval duration in radians per second, including roll. Times must increase strictly. Sampling must resolve less than pi radians per interval; complete turns can alias. Refine time spacing for time-varying demand. Assess feasibility using independently supplied speed, acceleration, travel, stability and platform/mechanism limits. The helper supplies no mechanical acceptance threshold.

## Instruments acquisition

`orsia_instruments.sample_lines_of_sight` uses Geometry's `compute_lines_of_sight` with default GCRS output. The caller supplies a timezone-aware UTC epoch, elapsed SI seconds, a GCRS trajectory and independent platform/instrument attitude laws. Instruments owns temporal/angular quadrature, exposure endpoints, sensor coordinates, image coordinates and measure weights. `LineOfSightSamples` retains the UTC epoch and GCRS ray/support arrays; scene providers attest continuous time/FOV/spectral coverage. Import analytic intersections directly from `orsia_geometry`. For WGS84 intersections of existing GCRS rays, use `transform_rays` first, or use `WGS84SurfaceProjection` when the consumer needs a fixed east/north chart. See the [moving-pixel example](../../orsia-instruments/docs/line-of-sight.md).

## Orbital adapters

Install `orsia-geometry[orbital]` for orbital/frame evaluation with SatKit 0.24.1. The base installation requires NumPy only. Imports stay deferred until an orbital/frame operation runs, preserving the array-only operations' import-cost and side-effect boundaries. Auxiliary coverage remains a separate operational requirement. Adapters internally convert elapsed SI seconds with continuous-duration addition to the UTC epoch. Native instants have microsecond resolution. An elapsed interval crossing a leap second retains its physical duration. Public signatures use UTC datetimes, scalar controls, Geometry records and NumPy arrays; native times, settings, quaternions, TLEs and results remain implementation details.

`frame_rotations` returns owned `(times,3,3)` matrices. Every non-identity transformation requires EOP status `observed` or `predicted`; missing, before-table and held/extrapolated values raise `RuntimeError`. `transform_states` computes `R @ v + Rdot @ r` using central differences of full rotations. Its half-step defaults to 0.5 s and must be at least `1e-4` s. Auxiliary coverage must include both shifted dates. This includes the small TEME-to-GCRS derivative term as well as Earth rotation. Native time/frame roundoff limits small-step refinement; the local 0.5 s versus 0.1 s comparison differs by less than `0.002 m/s`. Assess the step and resulting velocity error for the intended application.

`NumericalPropagator` accepts the six osculating elements `[a,e,i,RAAN,arg_periapsis,true_anomaly]`. Length is metres and angles are radians in GCRS. The finite closed accepted interval is forward from epoch and has a positive end. The constructor integrates from epoch through that end, then returns an evaluator over the accepted interval. The evaluator privately sorts native interpolation dates and restores requested order/repeats because the SatKit vector dense interpolator assumes chronological dates.

`NumericalPropagator(elements, *, epoch, validity_s, gravity_degree=2, gravity_order=0, sun_gravity=False, moon_gravity=False, absolute_tolerance=1e-4, relative_tolerance=1e-11)` selects EGM96 spherical-harmonic gravity and optional Sun/Moon third-body gravity. The degree and order satisfy `0 <= gravity_order <= gravity_degree <= 70`; degree zero gives the two-body limit. Both tolerances must be finite and positive. Absolute tolerance controls local integration error in metres for position components and metres per second for velocity components. Relative tolerance is dimensionless. Tolerances supply adaptive local error controls; global trajectory accuracy needs refinement and an appropriate physical model. The pinned SatKit 0.24.1 `python/src/pypropsettings.rs` defines the supported gravity truncation and native tolerance units.

Every construction creates fresh native settings with explicit EGM96, RKV98, dense interpolation and strict EOP coverage. Tides, relativity, space weather, drag, radiation pressure and thrust stay disabled. Changing either tolerance preserves the force choices. The backend also checks its padded precomputation nodes for EOP coverage. The object owns the native dense result and releases the result with its own lifetime. Construction may acquire public auxiliary files through SatKit; interpolation uses the retained result.

The former `settings` keyword and public `satkit_times` function are removed without compatibility aliases. Replace native settings with the scalar controls listed above. Public frame and trajectory calls take UTC epochs and elapsed SI seconds directly. Geometry's implementation-only `times` module has an empty `__all__`; its private `_native_instants` conversion is shared internally by frame and orbit adapters. The module is outside the supported public API. `SGP4MeanElements` and Data reader contracts remain unchanged.

`SGP4Propagator` accepts one immutable `SGP4MeanElements` record owned by Geometry. Its scalar values describe Earth-centred TEME/UTC mean elements, with angles in radians, mean motion in rad/s, full derivatives in rad/s² and rad/s³, and B* in inverse Earth radii. The constructor converts those values directly into a private SatKit record, reversing the source derivative factors 2 and 6, without textual TLE serialization. Propagation uses explicit WGS72/AFSPC SGP4. Data owns local GP OMM JSON/TLE parsing into this common contract; callers can also construct the record directly. The TEME state is transformed with the full reduction and rotation derivative, producing GCRS arrays. Native errors/nonfinite states fail explicitly. The caller supplies the accepted prediction interval and element-age policy. SGP4 physical SI elapsed time follows SatKit; across a leap second that convention differs from Vallado UTC-label subtraction by one second of propagation per crossing. The independent Vallado verification used here spans no leap-second crossing.

Both propagators expose immutable configuration bindings. `NumericalPropagator.elements` returns an independent writable copy of the initial elements; `SGP4Propagator.elements` retains the immutable scalar record. Native dense results and SGP4 records remain private. The direct constructors accept the same physical parameters as the former factories. Pointing laws remain independent callables.

### Callable-object migration

The former lowercase closure constructors are removed without compatibility aliases. Replace imports and calls with the following public APIs; constructor parameters, validation timing and numerical call contracts are preserved.

| Removed construction API | Direct replacement |
| --- | --- |
| `numerical_propagator(...)` | `NumericalPropagator(...)` |
| `sgp4_propagator(...)` | `SGP4Propagator(...)` |
| `wgs84_surface_projection(...)` | `WGS84SurfaceProjection(...)` |
| `wgs84_surface_projection_from_ray(...)` | `WGS84SurfaceProjection.from_ray(...)` |

Import these classes from `orsia_geometry` or their owning `orbits` and `surfaces` modules. Instruments retains `wgs84_surface_projection_from_camera(...)` because camera geometry belongs to that library; it returns `WGS84SurfaceProjection`.

## Resources, provider boundary and execution

Ordinary in-process SatKit use is supported. Offline operation and a dedicated worker are optional caller choices. SatKit searches its configured, installed, user and system directories and can lazily acquire normal public auxiliary files. Its EOP and JPL resources are process-global caches; changing directories or files does not establish that an already loaded cache changed. Python reports EOP coverage/status, but supplies neither the selected absolute EOP path nor an explicit-path EOP loader. Geometry therefore claims no exact loaded-file identity for that cache. Serialize native evaluation, auxiliary refresh and configuration changes; concurrent native-library scientific safety is unqualified. Geometry changes no global backend settings or download policy itself.

Data owns authenticated Space-Track access, local GP OMM JSON/TLE decoding, pure epoch-bound selection and native-byte provenance. Data depends on Geometry's scalar contract; Geometry imports neither Data nor authenticated providers. See [the Data orbital contract](../../orsia-data/docs/orbital-elements.md). The native reference recipe selects existing local DE421 and IERS EOP fixtures through process environment variables with offline mode. SatKit owns ordinary public auxiliary management; available-file identities remain independent of global cache selection.

## Bounded numerical evidence

The native reference suite uses SatKit 0.24.1 on CPython 3.14.3 free-threaded macOS arm64. Import and the exercised native calls retain a disabled GIL without a forced-off override. Installation reused an available UV artifact; this check establishes local install/import behavior and leaves other platforms and new source-build reproducibility unqualified.

The independent numerical fixtures are ERFA v2.0.1 `src/t_erfa_c.c:t_c2t06a`, the first three GMAT R2026A `leo_iss_j2.json` states retained in SatKit commit `441675131bf9b14a9634d069f7f2599b69c7252c`, and object 5 in CelesTrak's Vallado verification at commit `49df0479c950917c0a2c5ac31f2db6477bba57f6`. The tests cite the exact upstream files beside their constants. The ERFA test uses an artificial local EOP fixture to match specified TT/UT1/polar motion and isolates the reduction. GMAT compares a two-hour EGM96 degree/order 2 arc with Sun/Moon forces, tides/relativity disabled; the local ephemeris is DE421 while the reference used DE440. The comparison bounds are `0.1 m` position and `1e-4 m/s` velocity. A separate two-body circular limit has a `0.01 m` position bound, and dense-output tolerance refinement has a `0.1 m` bound. Vallado TEME state bounds are `0.02 m` and `2e-5 m/s`, accounting for published rounding and native epoch precision. These are bounded numerical checks; real GP prediction errors remain separate. The GCRS SGP4 adapter is checked against composition of the same native TEME state and frame transformation. An independent absolute TEME-to-GCRS state reference remains unavailable. Frame-velocity refinement uses the same backend and establishes internal consistency.

The illustrative near-nadir numerical allocation is `3 m`, chosen as 10% of a `30 m` reference sampling scale, independently of mission requirements. At 700 km height and 0.1 rad off-nadir, the analytic sensitivity test transports a 1 m position perturbation to less than 1.02 m ground displacement and a `1e-7 rad` direction perturbation to less than 0.08 m. Allowances of 1 m orbit, 0.1 m dense output, 0.1 m frame, 0.08 m attitude and 0.01 m arithmetic fit inside that allocation with margin. These allowances define a proposed numerical allocation for a synthetic, known-surface example. The single-direction spherical perturbation test illustrates sensitivity; it leaves the combined 3 m bound over the four WGS84 modes unverified. It excludes physical orbit/attitude knowledge errors, terrain, atmospheric ray bending and engineering feasibility. Direct public-API regressions in [`tests/test_orbital_reference.py`](../tests/test_orbital_reference.py) retain the former terrestrial example's four modes: nadir, platform tracking, instrument tracking and cross-track scan. The regressions check ground hits, rotating-target visibility, nonzero angular speed, tracking residuals and displacement during an illustrative 0.1 s exposure. They propagate classical osculating elements with the default EGM96 degree 2/order 0 model, then apply full dated ITRF rotations and WGS84 intersections. These synthetic trajectory and mechanism settings establish no instrument, retrieval or mission acceptance.
